### `background-blend-mode` actually blends

**`background-blend-mode` was an approximation and is now the real thing.** Every value but `normal`
used to clear the background colour and hand it to the image as a tint, so `multiply` and `hue` and
`difference` all produced the same picture and none of them produced a blend. Each background image
layer now blends with what is under it, through the same sixteen functions `mix-blend-mode` got, and
the colour is painted underneath as well as being blended with — it is the bottom of the stack, not
a value the image consumes. This corrects the previous entry, which described `plus-lighter` on a
background as tinting the image: it adds the layer to what is under it, exactly as it does on
`mix-blend-mode`.

The value is a **list**, one per background image layer in the order the images are given, repeating
when it is shorter than they are:

```css
background-image: url(res:noise), linear-gradient(gold, crimson);
background-blend-mode: overlay, normal;
```

The blend is weighted by what is underneath, as CSS specifies, so a layer with nothing behind it
comes through untouched — a single image over a transparent colour looks the same in every mode
rather than multiplying itself against black.

**The bottom layer costs nothing extra**, which is the case almost every use is. Its backdrop is the
background colour: a value the shader is simply handed, so it is exact, free, and identical under
both render pipelines. It is the layer above one that has to read back what was actually painted, and
an element only pays for that once it stacks two blended images. Then it rides the offscreen capture
`filter` and `mix-blend-mode` use, which also gives the CSS containment for free — the read happens
inside the element's own render target, so a layer blends with the layers below it and not with the
page the element is sitting on. Reading is a GrabPass on the built-in pipeline and the camera's
opaque texture under URP, and that texture holds no transparent UI, so **stacked blending needs the
built-in pipeline** while a single blended image works under both.

Riding the capture has one visible consequence CSS does not have: an element that stacks blended
layers becomes a blending group, so a descendant's `mix-blend-mode` stops there. CSS makes no
stacking context for `background-blend-mode`. A single blended image does not do it.

**The useragent stylesheet had been leaning on the old behaviour** and needed rewriting: a `toggle`
drew its tick by multiplying a white sprite against a black background colour, which under the old
rules meant "tint the image and drop the colour" and under CSS's rules means a solid black square
over the whole control. The tick is a `mask-image` now, which is what that was reaching for -- the
colour is what shows through the sprite, so it is also recolourable, where before it was black by
construction. Nothing rendered a checkbox in the suite, so nothing went red; `components/toggle` is
the snapshot that would have.

One thing that had to be unlearned along the way: a blending layer carries its backdrop in the vertex
colour rather than a tint, and UGUI drops a mesh whose vertex colour is fully transparent. A layer
blending against no background colour carries exactly that, and was being culled before it could
draw.
