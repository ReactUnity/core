### `mix-blend-mode`, and `isolation` grows a blending group

An element can now blend into whatever is painted behind it, with all sixteen CSS blend functions —
`multiply`, `screen`, `overlay`, `darken`, `lighten`, `color-dodge`, `color-burn`, `hard-light`,
`soft-light`, `difference`, `exclusion`, `hue`, `saturation`, `color` and `luminosity`. It takes the
same values `background-blend-mode` does, since CSS has one `<blend-mode>` type for both, plus
`plus-lighter`.

`plus-lighter` is not a blend function: rather than covering the backdrop by its alpha the element is
added to it and the sum is clamped, which is how two overlapping glows brighten each other instead of
the upper one winning. `screen` lightens along the same lines but tapers off (`a + b - ab`) and so
never clips, where this does. The element's own opacity scales what is added rather than the result,
which is the case that tells the two orderings apart — every unclamped one is the same either way.
CSS gives the keyword to `mix-blend-mode` alone; here one enum backs both properties, so
`background-blend-mode` parses it too, where it does what every other non-`normal` value does —
tint the image rather than paint behind it.

It rides the offscreen capture `filter` already uses, which is what makes it match the web: CSS
blends an element **and everything inside it as one image**, so a card's background, borders, text
and children go into the backdrop together rather than each blending against the ones drawn before
it. Setting both puts them in the order CSS gives them — the filter runs, and its result is what
blends.

**`isolation: isolate` now creates a blending group**, which is the same capture seen from the other
side: a descendant that blends can only read the backdrop the capture hands it, and outside the group
nothing changes. A `filter` on an ancestor contains a blend for the same reason. Blending between
siblings inside the group is untouched — isolating draws a boundary, it does not switch blending off.

`isolate` also keeps its ReactUnity-only meaning, not inheriting ancestors' `opacity` and
`pointer-events`. That needed carrying: the element's own `CanvasGroup` goes offscreen with the
subtree, where there are no parent groups left to ignore, so the flag now lives on the composite left
behind in the hierarchy. Without it an ancestor's opacity would have quietly started applying to an
element the moment it isolated.

`normal` costs nothing. An element only allocates the render target, and only pays for the backdrop
read, once it actually blends — the blending composite is a second shader, so a plain `filter` is
exactly as cheap as it was. Isolating does allocate the render target, since the containment is the
capture.

Reading the backdrop is a GrabPass on the built-in pipeline and the camera's opaque texture under
URP, the same split `backdrop-filter` has. Under URP that texture holds no other transparent UI, so
blending against a 3D scene behind the canvas works there while blending against another UI element
needs the built-in pipeline.
