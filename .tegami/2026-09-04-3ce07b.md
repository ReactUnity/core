### A code-split bundle loads out of Resources

**A lazy route's chunk now resolves.** A module usually has a url to resolve against — a dev server
serves the entry over http, and everything imported below it resolves there — but a bundle read out
of `Resources` had only the resource path it came from, which is relative, so nothing under it could
resolve and the first dynamic `import()` failed with `Could not resolve module './chunk.js'`. Those
modules get an origin of their own now, `resource:///assets/index.js`, which one relative resolution
serves the same way as an http url, and all three engines read that scheme back through
`Resources.Load` rather than a web request. ClearScript needed it on the document and not in its
loader, because a relative name is turned into a path under the current working directory before the
loader is ever asked.

**And the entry is registered under that url, so a chunk importing it back gets the module already
there.** A code-split chunk imports the entry for the runtime the two share, which under a bare
resource path named a module the engine did not have: it read the bundle again and evaluated a
second copy of it beside the first. Two renderers then held two sets of callbacks while the C# side
had ids for only one, so the first click on anything reported
`TypeError: cannot read property 'apply' of undefined` — with nothing in it to say a module had been
loaded twice. The WebGL backend shares the fix; ClearScript also caches what it reads, since a
chunk and its own importer otherwise read each other until the stack goes.

**`Event` is a global.** Bundler output reports a failed chunk by dispatching one and reading
`defaultPrevented` to decide whether to rethrow — Vite's dynamic-import wrapper does — so a chunk
that failed to load reported `Event is not defined` and the real reason was lost. `dispatchEvent`
now takes either an event or the type it has always taken. Only the event's own members are there;
there is no tree for it to travel through.
