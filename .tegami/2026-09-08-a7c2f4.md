### `position: sticky` and `position: fixed`

Both values have been in the `PositionType` enum since 2021 and neither did anything: `fixed` fell
through to `absolute`, so it answered to its parent and was clipped by an ancestor's `overflow`, and
`sticky` fell through to `relative`, so its insets shifted it in flow — the one thing sticky must
never do. Both are implemented for UGUI now.

A sticky box keeps its place in flow, and is then shifted the least it can be to stay inside the
nearest scroll container shrunk by its own insets, then clamped to its parent's content box — so it
is pushed back out at the end of a section the way a heading is. Its siblings never move for it.
Nothing about this reaches Yoga: a sticky element is laid out as `relative` and its insets are the
one set withheld from layout, then resolved against the live scroll offset after it, in the same
frame the scroll moves rather than a `motion-duration` behind it. An element with no scrollable
ancestor is not shifted at all.

```css
.header { position: sticky; top: 0; }
```

A fixed box is positioned against the host — the same box `vw` and `vh` measure — and is lifted out
of its parent, so an ancestor's `overflow: hidden` no longer clips it. Its slot in the parent is
held by a `display: none` stand-in node, which is the mechanism `<portal>` already used; that is
now shared, and along the way it fixes a latent bug where a portal's placeholder could be mistaken
for the portal itself when reordering siblings. Two consequences of the lift differ from a browser
and are deliberate: a lifted element no longer inherits an ancestor's `opacity`, `transform` or
`filter`, and with no insets it lands at the viewport origin rather than at its static position.

### `scroll-state(stuck: ...)`

The feature parsed and never held, because nothing was ever sticky. It now asks which edges of its
scrollport are holding the container, taking the same values `scrollable` does — a physical or
logical edge, an axis, `none`, or nothing at all for any edge. Like `scrollable` it is read off the
container itself, so the sticky element is the one carrying `container-type: scroll-state` and the
rules inside style what it contains.

```css
.header { position: sticky; top: 0; container-type: scroll-state; }

@container scroll-state(stuck: top) {
  .header .title { font-size: 14px; }
}
```

`snapped` still parses and never holds.

### UIToolkit: an unpositioned element was taken out of flow

`position: static` was read as `absolute` there, so an element that asked for the plainest possible
in-flow placement got the opposite. `static` and `sticky` are now `relative`, and `fixed` joins
`absolute`. UIElements has neither a sticky nor a viewport-relative position, so those
two degrade rather than being emulated: a sticky element under UIToolkit sits at its in-flow
position with its insets suppressed, and a fixed one behaves as `absolute`.

### A Kitchen Sink page for both

`Positioning` is a new page in the sample: a list of sticky section headers that are pushed out by
the end of their own section and light up their contents through `scroll-state(stuck: top)`, a
footer held against the bottom edge of a second scroll box, and two badges asking for the same
insets inside an `overflow: hidden` box -- the absolute one clipped by it, the fixed one drawn in
the corner of the whole viewport. Verified against the running sample: at a scroll offset of 60 in
a 261px port the held header covers the rows passing under it and its title reads the stuck state,
and at 130 -- past the last place a header fits in a 130px section -- it is clamped out of the port
and stops counting as stuck, with the next header taking its place.
