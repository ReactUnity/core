### oklch(), oklab(), color-mix() and @supports

**`oklch()` and `oklab()`** join `rgb()` and `hsl()` wherever a color is accepted, gradient stops included. Both take the modern space-separated syntax with an optional `/ alpha`, and the comma form too, for consistency with the functions already here. Lightness is a number or a percentage; chroma and the a/b axes are a number or a percentage of 0.4; hue is any angle unit. A `none` component resolves to zero.

The conversion is Björn Ottosson's, evaluated in double and narrowed at the end, and it agrees with a browser to the byte. Tailwind's `oklch(63.7% 0.237 25.331)` comes out as `#fb2c36` here, which is the hex Tailwind itself publishes for that swatch.

A color outside the sRGB gamut is clamped per channel, which shifts hue on a very saturated color. CSS Color 4 says to reduce chroma instead; that is not implemented, so treat a wide-gamut color as approximate.

**`color-mix()`** mixes two colors in `srgb`, `srgb-linear`, `hsl`, `oklab` or `oklch`. Both percentages are optional and may sit on either side of their color; one implies the other, and a pair summing under 100% scales the result's alpha by that sum. Alpha is premultiplied, so mixing with `transparent` fades rather than darkening. In the two polar spaces the hue may carry `shorter`, `longer`, `increasing` or `decreasing`, defaulting to `shorter`. Interpolation spaces this subset does not have, `lab` and `lch` among them, make the declaration invalid rather than silently mixing in the wrong space.

The colors themselves stay lazy, so `var()` and `currentColor` work as inputs to either function. The percentages have to be literal.

**`@supports` blocks are no longer dropped.** They were parsed and then ignored, so every rule inside one was lost. The condition is now evaluated — `and`, `or`, `not`, nesting, and declarations tested against ReactUnity's own properties and converters. That last part is the point: the underlying CSS parser can evaluate a condition itself, but only against the properties and values the web has, and this dialect is neither a subset nor a superset of that. It would have called `color-mix()` unsupported and `float` supported, both wrong here. Feature queries that are not declarations, `selector()` for one, evaluate to false.

`@supports` and `@media` now nest inside each other in either order, and a `@media` inside a `@media` matches only when both conditions do — previously the inner block's rules were dropped.

**On Tailwind v4, which is the obvious reason to want all this.** These functions are exactly what its output is made of: the palette is `oklch()` throughout, and every opacity utility is a `color-mix()`. Both now resolve, and a hand-authored stylesheet in that style works.

Its generated CSS still does not, for a reason none of this touches. Tailwind wraps its whole output in `@layer theme, base, components, utilities`, and `@layer` is not a rule the bundled ExCSS knows — it keeps the block's raw text but parses no rules out of it, so the contents never reach the styling layer. Unwrapping it means re-parsing that text and deciding what layer ordering does to the cascade, which is its own change rather than a detail of this one.

Worth knowing for when that lands: Tailwind guards its refined color with `@supports (color: color-mix(in lab, red, red))` written *inside* the style rule, as CSS nesting. ExCSS drops a nested at-rule while keeping the declarations around it, so the guard never reaches the evaluator added here and the unguarded declaration is what applies. That declaration is `color-mix(in srgb, oklch(…) 50%, transparent)`, which this change makes work — so the fallback path is the one that runs, and it is a close approximation of the oklab one rather than a hex.

Transitions and animations still interpolate colors in sRGB. Moving them to OKLab is a visible change to existing projects, so it is a separate decision.
