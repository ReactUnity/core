### oklch(), oklab(), lch(), lab(), color-mix() and @supports

**The four Lab-family color functions** — `oklch()`, `oklab()`, `lch()` and `lab()` — join `rgb()` and `hsl()` wherever a color is accepted, gradient stops included. All take the modern space-separated syntax with an optional `/ alpha`, and the comma form too, for consistency with the functions already here. Every component is a number or a percentage, and a `none` component resolves to zero. Hue is any angle unit.

What `100%` means differs by function, because each space has its own ranges: lightness is 0–1 in the OK pair and 0–100 in the CIE pair, and a full-scale chroma is 0.4, 0.4, 150 and 125 respectively. So `oklch(0.637 …)` and `oklch(63.7% …)` are one lightness, while in `lch()` both `54.29` and `54.29%` mean `54.29`.

The conversions are the published ones — Björn Ottosson's matrices for OKLab, and CSS Color 4's D50-referenced chain for CIE Lab — evaluated in double and narrowed at the end, and they agree with a browser to the byte. Tailwind's `oklch(63.7% 0.237 25.331)` comes out as `#fb2c36`, the hex Tailwind itself publishes for that swatch, and `red` converts to `lab(54.29% 80.8 69.89)`, the value CSS Color 4 publishes for it.

A color outside the sRGB gamut is clamped per channel, which shifts hue on a very saturated color. CSS Color 4 says to reduce chroma instead; that is not implemented, so treat a wide-gamut color as approximate.

**`color-mix()`** mixes two colors in `srgb`, `srgb-linear`, `hsl`, `lab`, `lch`, `oklab` or `oklch`. Both percentages are optional and may sit on either side of their color; one implies the other, and a pair summing under 100% scales the result's alpha by that sum. Alpha is premultiplied, so mixing with `transparent` fades rather than darkening. In the three polar spaces the hue may carry `shorter`, `longer`, `increasing` or `decreasing`, defaulting to `shorter`. The two worked examples CSS Color 5 publishes for `in lch` reproduce here to four significant figures. A space this subset does not have, `display-p3` and `rec2020` among them, makes the declaration invalid rather than silently mixing in the wrong one.

The colors themselves stay lazy, so `var()` and `currentColor` work as inputs to either function. The percentages have to be literal.

**`@supports` blocks are no longer dropped.** They were parsed and then ignored, so every rule inside one was lost. The condition is now evaluated — `and`, `or`, `not`, nesting, and declarations tested against ReactUnity's own properties and converters. That last part is the point: the underlying CSS parser can evaluate a condition itself, but only against the properties and values the web has, and this dialect is neither a subset nor a superset of that. It would have called `color-mix()` unsupported and `float` supported, both wrong here. Feature queries that are not declarations, `selector()` for one, evaluate to false.

`@supports` and `@media` now nest inside each other in either order, and a `@media` inside a `@media` matches only when both conditions do — previously the inner block's rules were dropped.

**On Tailwind v4, which is the obvious reason to want all this.** These functions are exactly what its output is made of: the palette is `oklch()` throughout, every opacity utility is a `color-mix()`, and the refined variant of each one is guarded on `@supports (color: color-mix(in lab, red, red))` — a condition that now answers true. All of it resolves, and a hand-authored stylesheet in that style works.

Transitions and animations still interpolate colors in sRGB. Moving them to OKLab is a visible change to existing projects, so it is a separate decision.
